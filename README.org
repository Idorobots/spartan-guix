* Spartan Guix

A GNU Guix channel for reusable packages, services and system images.

** Using the channel

Add this entry alongside Guix in the consumer's channel configuration:

#+begin_src scheme
(channel
 (name 'spartan-guix)
 (url "https://github.com/Idorobots/spartan-guix")
 (commit "REPLACE-WITH-PUBLISHED-COMMIT"))
#+end_src

** Raspberry Pi

=(gnu system images raspberrypi)= exports:

- =rpi-image-type=: discoverable as =rpi-raw= in an installed channel profile.
- =rpi3-barebones-os= and =rpi3-barebones-raw-image=.
- =%rpi-root-file-system=, =%rpi-boot-file-system= and
  =%rpi-resize-file-system-service= for compatible host configurations.

The Pi 3 OS includes the firmware -> U-Boot -> Linux boot chain, an ARM64
kernel and firmware, DHCP, OpenNTPD clock synchronization and automatic root
filesystem resizing. OpenNTPD uses Guix's default server pool. The image
uses MBR, a 256 MiB FAT32 =PIBOOT= partition mounted at =/boot/firmware=, and a
persistent ext4 =Guix= root partition last on the card.

=(spartan bootloader raspberrypi)= provides =u-boot-rpi-arm64-bootloader=.
The FAT initializer and deployment installer share a file-copy routine for
firmware, device trees, =u-boot.bin= and firmware configuration, dereferencing
symlinks for FAT. The Pi firmware loads U-Boot from this partition rather than
raw sectors. U-Boot's standard boot discovery reads
=/boot/extlinux/extlinux.conf= from the root filesystem and loads the selected
kernel and initrd directly. Guix's existing Extlinux generator supplies kernel
arguments, matching kernel device-tree directories and previous generations;
Guix installs the configuration atomically during updates.

With the channel and its dependencies installed, build the working-tree image:

#+begin_src sh
guix system image -L modules --target=aarch64-linux-gnu --root=pi3-barebones-image \
  modules/gnu/system/images/raspberrypi.scm
#+end_src

** Filesystem resizing

=(spartan services file-systems)= provides =resize-file-system-service-type=
and =resize-file-system-configuration= for any Guix System host using a plain
disk partition. It grows the partition with =growpart=, then grows the
filesystem. Device paths, filesystem labels and UUIDs are resolved through
Guix's filesystem helpers; the parent disk and partition number come from
Linux sysfs rather than device-name assumptions.

For example, add a service for a filesystem already declared in the host's
=file-systems= field:

#+begin_src scheme
(use-modules (gnu services)
             (gnu system file-systems)
             (spartan services file-systems))

(define data-file-system
  (file-system
   (device (file-system-label "data"))
   (mount-point "/data")
   (type "ext4")))

(service resize-file-system-service-type
         (resize-file-system-configuration
          (file-system data-file-system)))
#+end_src

The configured filesystem selects the tool at configuration generation time:

- =ext2=, =ext3= and =ext4=: =resize2fs= from =e2fsprogs=.
- =btrfs=: =btrfs filesystem resize max= on the configured mount point.
- =bcachefs=: =bcachefs device resize= on the resolved partition.

Each instance has a mount-point-specific Shepherd provision, so a host can
configure several filesystems. The service runs once after =user-processes=,
when filesystems are mounted. A =growpart= NOCHANGE result still runs the
filesystem resizer, allowing a later boot to recover from an interrupted
resize. Other partition-growth errors and filesystem-resize errors propagate.
Partitions can grow only into adjacent free space; the Pi image deliberately
places its root partition last. This service does not manage LVM volumes or
multi-device filesystems.

** Cross-compilation fixes and workarounds

The supported cross-build workflow uses =--target=aarch64-linux-gnu= on an
x86-64 build machine. The fixes below address failures in the pinned upstream
recipes; select their variants explicitly or use the Pi base OS, which integrates
the applicable image fixes. Run commands from this channel's root with
=-L modules= to test working-tree changes rather than an older installed channel.

*** Modules

1. *Time services: OpenNTPD baseline and cross-fixed reference NTP.*
   =modules/gnu/system/images/raspberrypi.scm= uses =openntpd-service-type=
   with Guix's default server pool. Hosts needing reference NTP's large initial
   clock adjustment (=ntpd -g=) can use:

   #+begin_src scheme
   (use-modules (gnu services networking) (spartan packages ntp))
   (service ntp-service-type
            (ntp-configuration (ntp ntp/cross-fixed)))
   #+end_src

   =ntp/cross-fixed= retains =update-leap= and its HTTPS dependencies. The
   =(spartan packages tls)= variant =perl-net-ssleay/cross-fixed= runs native
   Perl/MakeMaker with the target Perl configuration and headers, and probes
   native OpenSSL while linking target OpenSSL. A build-only Config overlay
   avoids loading target XS modules into native Perl. The dependency rewrite
   covers indirect SSL inputs through HTTP::Tiny and IO::Socket::SSL too.
   The overlay also supplies native =Errno.pm= with its architecture guard
   removed for build-time tools only; its constants must describe the machine
   executing those tools. This overlay is not installed in the target module.

   =(spartan packages perl)= supplies =perl/cross-fixed=: it installs the
   generated target XS headers and restores the preprocessor's =-P= option
   when parsing errno values. Without that flag, the pinned cross-built Perl
   produces an empty =Errno.pm= and HTTP::Tiny cannot load. Preprocessor input
   remains a filename rather than shell redirection, since the cross-build's
   miniperl cannot execute the target shell on the build machine. The NTP variant
   also embeds target Perl in script shebangs and target Guile and module
   paths in the =update-leap= wrapper. Native derivations remain identical
   to upstream for Perl, Net::SSLeay and NTP.

   These wrapper fixes address two failures after the XS build: configure could
   not find target Perl on the native executable search path, and =wrap-script=
   otherwise generated =#!#f= because native Guile was not an executable input.
   The package now supplies =PATH_PERL= explicitly and passes the target Guile
   path and target =PERL5LIB= directories to =wrap-script=.

   Build and check the cross package from this channel's directory:

   #+begin_src sh
   guix build -L modules --target=aarch64-linux-gnu \
     -e '(@ (spartan packages ntp) ntp/cross-fixed)'
   # With Python 3, native openssl, and qemu-aarch64 available:
   python3 tests/ntp-cross-runtime.py /gnu/store/…-ntp-4.2.8p18 /path/to/qemu-aarch64
   #+end_src

   The runtime check loads the target XS module, checks errno constants,
   runs =ntpd --version= and =update-leap -h=, downloads over loopback HTTPS
   with certificate verification, and verifies rejection of an untrusted
   certificate. It does not change the machine's clock or require binfmt.

2. *OpenNTPD: the local =openntpd/cross-fixed= package variant.*
   =modules/spartan/packages/ntp.scm= inherits upstream OpenNTPD and replaces
   two build phases:
   - =fix-update-script= selects =/bin/sh= from native inputs for the
     build-time bootstrap script, falling back to ordinary inputs for native
     builds. It retains upstream's substitution disabling the Git invocation.
   - =adjust-C_INCLUDE_PATH= removes the raw OpenBSD source-header directory
     from both =C_INCLUDE_PATH= and =CROSS_C_INCLUDE_PATH=. Upstream only
     adjusted the former, so cross-compilation picked up incompatible headers
     and failed with =sys/_null.h: No such file or directory=.

3. *Filesystem resizing: select tool dependencies before constructing gexps.*
   =modules/spartan/services/file-systems.scm= supplies the channel's
   =resize-file-system-service-type=. The upstream service retained all
   filesystem tools through runtime dispatch, including broken cross-build
   dependencies of =bcachefs-tools= for an ext4 root. The replacement selects
   only the applicable tool: =e2fsprogs=, =btrfs-progs= or =bcachefs-tools=,
   together with =cloud-utils=. The Pi therefore avoids the unused bcachefs
   Rust/Clang dependency graph. These tool packages are otherwise unmodified.

4. *libcbor: select target CMocka when cross-compiling.*
   =(spartan packages compression)= provides =libcbor/cross-fixed=. Guix commit
   =ebba73d4f78140c9489b71583376d59cf0a28951= enabled libcbor's tests but put
   CMocka in =native-inputs=. The test executables link against CMocka, so
   cross-builds need the target library. The variant moves CMocka to =inputs=
   only for cross-builds, retaining upstream configure flags and test
   compilation. Guix's CMake cross build system skips test execution by default.
   Native builds retain the upstream derivation and test behavior.

   =package-with-cross-fixed-libcbor= rewrites explicit transitive dependencies,
   including =OpenSSH -> libfido2 -> libcbor=. Consumers can select it with
   =(openssh (package-with-cross-fixed-libcbor openssh))= in an
   =openssh-configuration=. This does not rewrite implicit build tools.

5. *Resize service: include the channel's runtime module in its closure.*
   The same service explicitly includes the =spartan= namespace when computing
   its source-module closure. Guix's default selector includes only =gnu= and
   =guix= modules, which omitted =(spartan build file-systems)= and caused
   compilation of =shepherd-resize-file-system--.go= to fail. This is a
   module-packaging fix relevant to native builds as well as cross-builds.

6. *Pi bootloader: use U-Boot with Extlinux instead of the EFI/GRUB chain.*
   =modules/spartan/bootloader/raspberrypi.scm= provides
   =u-boot-rpi-arm64-bootloader= using stock =u-boot-rpi-arm64-bin= and
   =raspberrypi-firmware=. The upstream =grub-efi-netboot-removable-bootloader=
   package executed the target =grub-mknetdir= on the build machine. The channel
   assembles boot files with native Scheme code and uses Guix's existing Extlinux
   generator to load Linux directly.

7. *ALSA: keep bootstrap tools native and udev's cat on the target.*
   The pinned =alsa-lib= Git recipe places Autoconf, Automake and Libtool in
   target inputs despite executing them during bootstrap. This unnecessarily
   cross-builds Automake, whose =t/strip2.sh= test compiles an AArch64 program
   and then invokes native =strip=, failing with an unrecognized file format.
   =(spartan packages linux)= provides =alsa-lib/cross-fixed=, which moves
   these three tools to native inputs for cross builds. This also makes
   ALSA's bootstrap executable on the build machine.

   =alsa-utils/cross-fixed= selects the corrected library and explicitly adds
   target =coreutils-minimal= for =cat= in the installed udev rule.
   =package-with-cross-fixed-alsa= rewrites explicit dependencies, and the Pi
   base OS applies it to its udev rules. No tests are disabled, audio rules
   are retained, and native ALSA recipes are unchanged.
   Adding target =coreutils-minimal= also fixes the subsequent
   =patch-alsactl-udev-rules= failure looking for =bin/cat= in target inputs.

8. *Groff: use native formatters to build documentation.*
   =groff-minimal= 1.24.0 still builds documentation: its inherited
   =--with-doc=no= flag is no longer recognized upstream. The stock cross
   make flags supply =GROFFBIN= but leave =pdfmom='s =GROFF_COMMAND= set to
   =test-groff=, which is absent from the executable search path and would
   invoke target binaries if found. =(spartan packages groff)= provides
   =groff/cross-fixed= and =groff-minimal/cross-fixed=. Cross builds select
   native =groff= and =pdfmom=, set =GROFF_BIN_PATH= to the native =bin/=
   directory, and make =GROFF_COMMAND= follow =GROFFBIN=. Documentation is
   retained and native derivations are unchanged. The Pi base OS applies
   =package-with-cross-fixed-groff= to its packages, including =man-db=.

   Apply this rewrite before =package-with-cortex-a53-guile= when composing
   both helpers. The latter can clone dependencies, so applying the Groff
   replacement afterward can miss the original package objects. The Pi base
   OS uses =(compose package-with-cortex-a53-guile
   package-with-cross-fixed-groff)= to preserve both fixes.

9. *BIND: omit the obsolete target PLY dependency.*
   =(spartan packages dns)= provides =isc-bind/cross-fixed=. The pinned BIND
   9.19.24 recipe lists =python-ply= in target inputs, but that source release
   no longer contains the old =isc= Python module that used PLY. The only
   PLY references in its release archive are historical changelog entries.
   The stale input causes even image =--dry-run= to fail during lowering:

   #+begin_example
   python-ply@3.11: build system `pyproject' does not support cross builds
   #+end_example

   The variant removes only =python-ply= from cross-build inputs. It retains
   Python, all build phases, the =out= and =utils= outputs, and BIND's DNS
   utilities. Native derivations remain identical to upstream. The homelab
   Pi management host selects this variant for its additional BIND package;
   the channel's barebones OS does not include BIND. This is a correction to
   BIND's dependency list, not general cross-build support for =pyproject=.

*** Verification and current image-build status

The reference NTP, ALSA library/utilities, minimal Groff, and BIND variants have
successfully cross-built from x86-64 to AArch64. The NTP runtime check above
verifies that the compiled XS extension works with target Perl and OpenSSL,
including certificate-verified HTTPS and rejection of an untrusted certificate.
The cross-built =troff= also formatted text under AArch64 QEMU, and BIND's
=named -v= and =dig -v= ran successfully under the same emulator.

=tests/ntp.scm=, =tests/linux.scm=, =tests/groff.scm=, and =tests/dns.scm= check
dependency selection and unchanged native x86-64/AArch64 derivations. The image tests
check selection of the corrected udev rules and =man-db= dependency before
and after image conversion. The SRFI-64 suites and selected Guix lint checks
passed; these checks do not constitute a boot test or a complete image build.
BIND retains upstream lint findings for its =nghttp2= input label and its
=check= phase not honoring =#:tests?=; the cross variant does not alter those
phases or native recipes.

For isolated package builds from this channel's root:

#+begin_src sh
guix build -L modules --target=aarch64-linux-gnu --no-grafts \
  -e '(@ (spartan packages ntp) ntp/cross-fixed)'
guix build -L modules --target=aarch64-linux-gnu --no-grafts \
  -e '(@ (spartan packages linux) alsa-utils/cross-fixed)'
guix build -L modules --target=aarch64-linux-gnu --no-grafts \
  -e '(@ (spartan packages groff) groff-minimal/cross-fixed)'
guix build -L modules --target=aarch64-linux-gnu --no-grafts \
  -e '(@ (spartan packages dns) isc-bind/cross-fixed)'
#+end_src

With these fixes selected, the homelab's Pi management image =--dry-run=
successfully lowers its dependency graph and reports the pending builds and
downloads. A completed dry run does not establish that every remaining package
builds or that the resulting image boots on hardware.

*** Related image and runtime corrections

1. The boot-file bundle explicitly sets =arm_64bit=1= in the last firmware
   configuration include: upstream's initial value can reflect the x86 machine
   that loaded the module. Its shared image/deployment installer dereferences
   symlinks for FAT and installs =u-boot.bin= as a file. The image keeps the FAT
   partition at MBR type =0x0C= and mounted at =/boot/firmware=, avoiding Guix's
   special =/boot/efi= rewriting. These address boot-image construction, not CPU
   emulation.

2. The replacement resize implementation also resolves device aliases and parent
   partitions, waits for the relevant mount, uses
   =btrfs filesystem resize max MOUNT-POINT=, and retries filesystem growth after
   =growpart= reports NOCHANGE.
   Those are runtime correctness fixes, independent of cross-compilation.

*** Cortex-A53 Guile linker workaround

=(spartan packages guile)= provides =guile-3.0/cortex-a53= and
=guile-3.0-latest/cortex-a53=. They retain the upstream versions and build
settings, appending =-Wl,--fix-cortex-a53-843419= to =LDFLAGS= only when
building for AArch64, natively or by cross-compilation. Existing linker flags
are preserved. JIT support remains enabled.

The Pi 3 OS uses =package-with-cortex-a53-guile= for its system packages,
Guix service package and Shepherd runtime, including their explicit Guile
extension dependencies. The Shepherd override belongs in =essential-services=
so it replaces the default instance rather than adding a second root service.
Consumers adding Guile-dependent packages should apply the same helper.
This does not globally replace Guix's default interpreter for generated boot
scripts or implicit build-system inputs.

This addresses a suspected Cortex-A53 erratum 843419 sequence in compiled
=libguile= code. The linker can rewrite susceptible =ADRP= sequences or insert
veneers; it does not process machine code emitted later by the JIT.

** Development and tests

With GNU Make and the channel's dependencies installed, run from this repository
root:

#+begin_src sh
make check check-image
#+end_src

=make check= runs every =tests/*.scm= SRFI-64 suite. These exercise service
graphs, partition layout and mounts, root resizing, the real boot initializer,
the 64-bit firmware override, resize command execution and filesystem-specific
tool dependencies. Resize tests use a synthetic sysfs tree and harmless
commands, requiring no block devices or root privileges.
=make check-image= lowers the AArch64 image derivation without building a kernel
or SD image. Override =TARGET= to evaluate another cross target where supported.

For a Guix matching CI's revision, with a separate pinned Nonguix checkout:

#+begin_src sh
make check check-image GUIX_LOAD_FLAGS='-L /absolute/path/to/nonguix'
#+end_src

To test the committed checkout as an installed channel, including Guix's real
named-image discovery:

#+begin_src sh
SPARTAN_GUIX_COMMIT="$(git rev-parse HEAD)" \
  guix repl ci/channels.scm > channels-ci.scm
make check check-image check-discovery \
  GUIX='guix time-machine -C channels-ci.scm --'
#+end_src

=ci/channels.scm= emits a channel list containing the tested Guix revision and
a local Git URL at the exact commit from =SPARTAN_GUIX_COMMIT= or =GITHUB_SHA=.
Guix resolves runtime dependencies from the committed =.guix-channel=.
The generated file works with Guix's isolated channel evaluator. Commit the
channel changes before using this bootstrap; it loads committed source.
The ordinary =check= and =check-image= targets exercise working-tree source
through =-L modules=.

GitHub Actions runs this real-channel bootstrap, all regression tests, the
cross-build graph and named discovery on pushes to =main=, pull requests and
manual dispatch. Actions are commit-pinned, with Dependabot updates enabled.
CI evaluation is separate from a full image build and hardware boot testing.

When contributing packages, include source hashes and package license metadata,
add meaningful checks under =tests/=, and run =guix lint= for the new package.
When changing upstream revisions, update CI's Guix pin in =ci/channels.scm=
and the runtime dependency revisions in =.guix-channel= as needed, then run all
checks. Deployment locks belong in consumer repositories.
